# Summary

This report refreshes the SchoolCity-to-PIE tool comparison using the [master gap-analysis document](https://renlearncrm-my.sharepoint.com/personal/justin_elston_renaissance_com/_layouts/15/Doc.aspx?sourcedoc=%7B41F7ACE6-1D81-40D5-91CE-DBC5D6BDD811%7D&file=SchoolCity%20and%20PIE%20Items%20gap%20analysis%20-%20visual%20examples.docx&action=default&mobileredirect=true) as the source of truth for SchoolCity behavior and visuals, while using this repository as the source of truth for the current PIE Players state. It also adds a Learnosity parity lens based on public Learnosity documentation and live screenshots from a local Pieoneer Learnosity Items API preview.

Reviewed and extended 2026-08-15. The SchoolCity column is now checked against the implementing source — `sc-online-testing`, `sc-suite-student`, `sc-suite-staff` and the three `sc-texttospeech-*` repositories — rather than the master document alone, and the Learnosity column against current documentation. Where the two disagree the row says so. Claims sourced from code are marked as verified in code; claims sourced from documentation are marked as documented, and the two are not merged.

Corrected 2026-08-16 on three rows. All three claims survived the August source-verification pass and failed only when someone implemented against the row, so reading a file for what it declares is a weaker check than reading it against the elements this repository renders. PIE-479's gap is discovery, not selection: voice selection was already plumbed. PIE-478's stylesheet was not merely unwired but aimed at an element this repository does not render, and regressed heading sizes wherever a host did apply it. And PIE-472's "scheme count" delta is eleven host-registrable overlays costing 2 to 18 tokens each, not eleven missing framework palettes. Jira was read for those three stories, which the [verification record](./schoolcity-parity-verification-record-2026-08.md) had noted as not consulted; PIE-472's status contradicted the table and now says so.

The main conclusion is unchanged in shape: PIE Players has reusable packaged tools for the core visual, measurement, and reference overlay set — theme/color schemes, line reader, annotation/highlighting, answer eliminator, ruler, protractor, graph, periodic table, and both dictionaries — and SchoolCity’s student tool surface remains broader, including translation tools, notes/comments, flags, writing checklists, resources, rollovers/pop-ups, magnifier, spell check, speech-to-text, media upload, robust response-editing controls, and item-authoring controls that are not packaged PIE toolkit tools today.

Four things changed the balance since the June pass, and the claim that read-aloud is the *only* area favoring PIE no longer holds.

- **Formative delivery shipped.** PIE now has a per-item Try budget, feedback reveal as an `env` projection, and a section mastery rollup, with a student-facing check-answer control. The June pass had no row for check-answer because PIE had no such capability; Learnosity does, and this closes it.
- **Two content accommodations shipped, and one exceeds both comparators.** A sign-language (ASL) region and an audio transcript are delivered through the QTI accessibility-catalog rail as policy-gated capabilities. SchoolCity has no signing capability anywhere in its source, so this is the second area where PIE leads rather than trails.
- **Theming and color schemes went from partial to substantially delivered** — ten built-in schemes plus custom registration over a unified resolution path, against six documented for Learnosity and fifteen for SchoolCity.
- **Text-to-speech still favors PIE, with one claim corrected.** Speech-mark fidelity is not uniform across providers as the June pass stated: only the Polly provider delivers authored SSML and native millisecond word offsets simultaneously.

Two findings cut the other way. Learnosity's response-type breadth remains the durable gap and is now quantified — 41 documented question types against 30 PIE elements, including audio recording, video recording and file upload, for which PIE has no equivalent in either repository. And PIE models no assessment time at all, while SchoolCity delivers extended time live over a proctor channel; that is a session model, not a tool.

Two of the master document's rows did not survive source review, which is the strongest argument for treating it as one input rather than the source of truth: "Browser Zoom Support" exists in none of the three SchoolCity repositories and appears to be the magnifier under its real name, and "Picture Dictionary" is already served by a PIE API endpoint, making it a missing player surface over an existing PIE backend rather than a missing capability — a surface that has since been built.

The relevant Renaissance replacement path is a combination of:

- PIE Players toolkit behavior for reusable tools and custom elements.
- Quiz Engine or another assessment host for product chrome, test navigation, flagging, global settings, and tool placement decisions.
- PIE items and response editors for item-owned editing controls such as equation input, spell check, media upload, drawing, and robust text editing.

Quiz Engine status is treated here as product delivery context only. This report does not re-audit Quiz Engine implementation details. Learnosity is treated as an external benchmark for assessment-player tool placement, not as a target for wholesale feature cloning.

## How To Read The Classifications

- **Strong** means PIE has a packaged tool with the same core student purpose.
- **Partial** means PIE has related capability, but discovery, placement, interaction model, or scope differs materially.
- **Missing** means no packaged PIE toolkit tool currently covers the SchoolCity capability.
- **Host-owned** means the capability belongs in assessment chrome, Quiz Engine, navigation, content rendering, or product configuration rather than a reusable PIE toolkit tool.
- **Item-owned** means the capability belongs in PIE item rendering, authoring, or response editors.
- **Out of parity scope** means the master document includes the row, but this comparison is not treating it as a gap to solve in this report.

## Text to Speech (Read Aloud)

Text-to-speech is the one area in this comparison where PIE Players clearly leads an application-specific implementation rather than trailing it. SchoolCity’s read-aloud is a product-specific front-end wired directly to the SchoolCity TTS backend. PIE reaches that same backend through the `@pie-players/tts-server-sc` custom-backend adapter — but in PIE the SchoolCity service is just one pluggable provider behind a reusable, standards-aligned TTS subsystem that ships with the toolkit and is shared with the QTI player in `pie-qti`.

The SchoolCity service is narrower than "a TTS backend" suggests, and reading its source rather than the master document settles what the adapter is actually integrating with. It is a two-route Fastify app — `GET /ping` and an authenticated `POST /` — over **AWS Polly only** (`sc-texttospeech-api/src/api/polly.js:38-48`), which the Terraform confirms: the ECS task role's sole TTS grant is `AmazonPollyReadOnlyAccess` (`sc-texttospeech-terraform/role.tf:78-80`). It supports 29 locales with one default Polly voice each (`sc-texttospeech-api/src/helpers/voices.js:1-31`), always sends `TextType: "ssml"`, and caches to S3/DynamoDB keyed on a hash of the transformed text. So PIE's "multi-backend" claim is a property of PIE, not inherited from SchoolCity — the SchoolCity side is single-engine.

Two consequences for the parity read, both verified in source rather than documented anywhere:

- **SchoolCity has no pronunciation store.** No lexicon endpoint, no `LexiconNames` on any Polly call, and none is provisionable — the Polly read-only role excludes `polly:PutLexicon`. SchoolCity's "Custom Speech" and "Text to Speech Pronunciation" are authored in the SchoolCity app and arrive at the service as SSML-bearing request text; `phoneme`, `sub`, `say-as`, `prosody`, `emphasis` and `lang` are in the service's permitted tag set (`sc-texttospeech-api/src/api/polly.js:387-392`). PIE's QTI-catalog path is therefore the same mechanism — author-supplied SSML at request time — moved onto a standards-based carrier, which is a stronger claim than the June pass made and rests on the same evidence.
- **PIE's production access to this service is not established from these repositories.** The service authorizes by JWT issuer against a per-issuer secret map. On `main` and `stage` that map holds `sc`, `dna` and `archivists` only; `pie-api` and `knowledge-check` exist on the `dev` branch (`sc-texttospeech-api/src/configurations/shared-secret.js`), and the Terraform variables provisioning their secrets exist only on an unmerged branch. The in-repo consumer is the section-demos route (`apps/section-demos/src/routes/api/tts/sc/+server.ts:139-154`). Whether a Renaissance production deployment uses this path is outside what these repositories show.

Capabilities verified in this repository:

- **Pluggable, multi-backend providers.** A zero-dependency core interface (`@pie-players/pie-tts`) with shipped server providers for AWS Polly (`tts-server-polly`) and Google Cloud TTS (`tts-server-google`), the SchoolCity-backed adapter (`tts-server-sc`), and a browser-side client (`tts-client-server`). Any backend can be added by implementing the same provider interface.
- **Always-available browser fallback.** The toolkit always includes a Web Speech API provider, so read-aloud works with zero server configuration and degrades gracefully when a server provider is unavailable — an improvement over a single hard-wired backend.
- **Word- and block-level highlighting, with per-provider fidelity.** The highlight pipeline picks the smallest reliable visible target and falls back through sentence, region, and whole-formula blocks rather than ever showing a wrong or lagging highlight. Speech-mark quality is not uniform across providers, and the June pass stated it as if it were: Polly returns native millisecond word marks (`packages/tts-server-polly/src/PollyServerProvider.ts:305-312`); Google derives marks by injecting `<mark>` before every word and reading SSML timepoints (`packages/tts-server-google/src/GoogleCloudTTSProvider.ts:416-461`), returns none at all for Studio voices (`:212`, `:250-271`), and **discards authored SSML on the marks path** — `extractWordsFromSSML` strips every tag and re-injects marks over plain text (`:467-484`), which is the default since `includeSpeechMarks` defaults on; the SchoolCity adapter returns millisecond times with best-effort character offsets, rebased by a single scalar shift derived from a median of token matches (`packages/tts-server-sc/src/SchoolCityServerProvider.ts:549-564`), which drifts silently whenever the service's SSML sanitizer changes interior length. Only `tts-server-polly` delivers authored SSML and correct native offsets at the same time.
- **Mixed DOM + SSML model, aligned to QTI.** PIE reads visible DOM text directly and also plays authored SSML supplied through QTI 3.0 accessibility catalogs (`data-catalog-idref` + `<speak>`), mixing the two per region. `SSMLExtractor` can lift inline `<speak>` markup into catalogs. This authored-pronunciation path is exactly what SchoolCity’s “Custom Speech” and “Text to Speech Pronunciation” markup cover.
- **On-the-fly math speech.** Rendered MathML is converted to natural-language speech with the Speech Rule Engine (ClearSpeak), plus a math alignment plan so formulas can be highlighted glyph-by-glyph or as a whole-formula block — high-fidelity math read-aloud without pre-recorded audio.
- **Recorded audio as a `spoken` alternate**, added since the June pass. QTI 3 treats synthesis and a human recording as the same support, so a `spoken` card can now carry a `MediaAssetRef` of `kind: "audio"` plus an optional time range instead of a reading script, needing no new PNP entitlement. Highlighting for a clip is the docked node as a block for the clip's duration — a recording emits no word-boundary events, and deriving them from duration would highlight the wrong words confidently rather than the right region vaguely. A failed clip falls back to the synthesized path. This closes the gap for programs that require a human voice.
- **Content that is shown but never spoken.** `data-tts-suppress` (`packages/assessment-toolkit/src/services/tts/text-processing.ts:98`) excludes a region from read-aloud while leaving it visible, which is what a passage-internal answer key or a decorative label needs.
- **Customizable control bar.** Hosts can configure any number of inline speed buttons (with custom labels), hide them entirely, and choose placement via layout modes (`reserved-row`, `expanding-row`, `floating-overlay`, `left-aligned`), alongside voice, rate, language, and engine settings.
- **Instrumentation and QA tooling.** The TTS service emits telemetry, and the toolkit ships a reusable settings/preview panel (`section-player-tools-tts-settings`) plus an instrumentation debugger for validating providers, voices, speech marks, and highlighting inside a host.

The Learnosity comparison is favorable as well, and rechecked against current documentation it still holds. Read-aloud in Learnosity is delivered through marketplace partner integrations — [ReadSpeaker](https://learnosity.com/company/partners/partners-directory/readspeaker/) and Everway/Texthelp’s [SpeechStream](https://learnosity.com/company/partners/texthelp/) — rather than a native first-party engine. Those partners do offer word/sentence highlighting and math reading, but as separately licensed third-party products layered onto the platform. Learnosity’s own [accessibility authoring guidance](https://help.learnosity.com/hc/en-us/articles/29581962023197-Authoring-for-Accessibility) claims screen-reader support and author-supplied transcripts, not synthesis.

Two Learnosity features are adjacent enough to misread as first-party read-aloud, and neither is. The `audioplayer` [feature](https://help.learnosity.com/hc/en-us/articles/16685246517277-Audio-player) plays pre-recorded, author-supplied audio; the `audio` [question type](https://help.learnosity.com/hc/en-us/articles/16685294938909-Audio-recorder-audio) records the learner’s voice. Separately, first-party **SpokenMath** generates textual descriptions of formulas for an external screen reader — text out, not audio, so it is not an engine.

PIE instead ships read-aloud as a first-party, standards-aligned subsystem with swappable backends, authored SSML plus generated math speech, and a customizable control bar. PIE’s mixed DOM/SSML-catalog model aligned to the QTI standard goes beyond what SchoolCity’s app-specific front-end exposes and, as far as public documentation shows, beyond what Learnosity surfaces as a built-in capability. PIE now also plays a human recording through the same `spoken` support, which is the form the partner products are usually licensed to avoid.

## Formative Delivery And Check-Answer

The June pass had no row for check-answer or instant feedback, and PIE had no such capability to give one. It landed in `fc71c915`: a per-item Try budget, feedback reveal, and a section mastery rollup. The contract is [`../prds/formative-delivery-contract.md`](../prds/formative-delivery-contract.md) and the host-facing surface is documented in [`packages/section-player/README.md`](../../packages/section-player/README.md).

What was missing was never evaluation. `scorePieItem(...)` already called each element controller's `outcome(...)` under `mode: "evaluate"`, and `pie-item-player.provideScore()` already exposed it imperatively. The gap was the delivery state around it: how many times a learner may submit one item, when its feedback becomes visible, and how a section reports how much was mastered.

**Try** is the unit: one submitted-for-checking pass over one item. Named Try rather than attempt because `TestAttemptSession` is the assessment administration and `TestAttemptItemSession.attemptCount` counts distinct PIE session ids, so a third sense of "attempt" would be misread as one of those. Authoring is one optional field — `AssessmentSection.formative` sets the section default and `AssessmentItemRef.formative` overrides it field by field. Absent, or `enabled: false`, and delivery is byte-identical to before.

**Feedback reveal is an `env` projection, not a UI.** PIE renders no feedback of its own: a revealed item gets `mode: "evaluate"` over the section env, with `role: "instructor"` under `feedback: "solution"` — the element convention for also showing the authored correct response — and the element draws the rest. `env.role` selects a rendering and has never been an authorization boundary; the host decides whether a learner may see solutions by setting the policy, and PIE enforces that by not projecting the role otherwise.

**Mastery excludes what it cannot score.** Correctness is derived, never authored, and has four values — `correct`, `partial`, `incorrect`, `unknown`. An item holding a rubric element, or one whose bundle exposes no `outcome`, is `unknown` rather than `incorrect`, and the rollup drops it from the denominator instead of reporting a false negative. An untried item stays in the denominator, which is what keeps a section from reading as mastered after one correct answer.

The student-facing control is real and shipped: `SectionItemCard.svelte:219-223` renders a "Check answer" button that becomes "Try again" once a Try is spent, with tries-remaining and correctness announced in words rather than colour alone.

The vocabulary maps onto QTI 3 so a `pie-qti` adapter inherits it — `maxTries` to `qti-item-session-control@max-attempts` (`"unlimited"` ↔ `0`), `feedback` to `show-feedback` / `show-solution`, `tryCount` to item session `numAttempts`. No conformance is claimed. QTI's `allow-comment`, `allow-skipping` and `validate-responses` are unrepresented, because there is no candidate-comment surface, no skip gate and no response-validation step to honour them with.

Two boundaries bound the capability. Scoring is client-side: correctness is derived in the browser from the item model, which is the same exposure Learnosity closed in 2026.1.LTS with encrypted Check Answer validation, and the PRD lists server-authoritative scoring as an explicit non-goal. And branching is out of scope — making the next item depend on correctness is separate ground for which Try state is the prerequisite.

Against SchoolCity this is not a master-document row at all, so there is no parity verdict to give; it is a capability PIE now has and the June pass could not have credited.

## Element-Level Translation And The Translation Rows

The translation rows below (PIE-474, PIE-481) are usually read as needing a translation tool. They also need translated element chrome, and the two halves are in different repositories with different coverage.

`packages/players-shared/src/i18n` covers en/es/zh/ar with RTL (`loader.ts:18`, applied to the document at `simple-i18n.ts:167`) and `Intl.PluralRules` pluralization (`simple-i18n.ts:213-217`). Coverage inside pie-players is thinner than that infrastructure implies: the only consumer is the toolkit's `I18nService`. Tool registrations hardcode their labels — `name: "Ruler"` at `packages/default-tool-loaders/src/registrations/measurement-tools.ts:37` — while `translations/*/tools.json` carries `tool.ruler` and `tool.ruler_aria` already translated into all four locales. Section-player's formative strings are hardcoded English too ("Check answer", "Try again", "1 try left."). So the catalog is written and largely unread.

In `pie-elements-ng` element-level i18n exists and is partial. `@pie-lib/translator` (`packages/lib-react/translator/src/index.ts:11-23`) is an i18next instance with en + es bundles, locale normalization and plural suffixes, wired into 10 of 30 element packages and 5 delivery libs — delivery code, not only authoring. Alongside it, substantial user-facing English is hardcoded in the same files that translate other strings: `math-inline/src/controller/index.ts:237` calls `translator.t(...)` while lines 383-405 hardcode `'This field is required.'`; delivery `aria-label`s such as `'Math Response Question'` (`math-inline/src/delivery/index.ts:83`) and `'Written Response Question'` (`extended-text-entry/src/delivery/index.ts:101`) are literals. No Svelte element uses the translator.

The consequence for the parity rows: a selected-text translation tool or a full-assessment translation pass operates on authored content and would leave element chrome in English. SchoolCity's own answer is instructive here — its full-assessment translation is the public Google Translate widget over the rendered DOM (see [Translation And Dictionaries](#translation-and-dictionaries)), which translates chrome and content alike precisely because it does not distinguish them.

## SchoolCity Capabilities Outside The Tool Rows

The master document is tool-by-tool, so it captured toolbar buttons and missed student-facing behavior that is not one. Everything here is verified in `sc-*` source and has no row above. Ordered by how much it should affect PIE planning.

**Time is a delivered, live-controlled capability, not a setting.** A proctor changes a running test: `sc-online-testing/stores/exam/socketStore.ts:139-180` handles `TIMER_PAUSE`, `TIMER_START`, `TIMER_CHANGE_DURATION`, `TIME_OUT`, `SESSION_TIME_OFF`, `STOP` and `TIMER_DISABLE` over socket.io, with the student joined to a per-user room. Extended time arrives mid-test. Section timers are separate, on `AssessmentSession.DurationMinutes`. Nothing in the PIE assessment toolkit models time at all — no section timer, no extended time, no break timer — which makes PIE-467 and PIE-482 larger than a tool row: the gap is a session-time model plus a live control channel, and the break-timer concept does not exist on the SchoolCity side either (the model is pause/resume plus a proctor top-up increment).

**Accommodation profiles are a full subsystem, and the domain does not call them IEP or 504.** The terms are **Accommodation Template** and **Student Profiler** (`sc-suite-staff/WebContent/WEB-INF/Javascript/common/AccommodationSettings.js`, ~1400 lines; `java/com/schoolcity/stars/dao/admin/AccommodationTemplateDAOImpl.java`). Per student: `OnlineDurationMinutes` (extended time), `OnlineTimeIncrement` (proctor top-up), time and day windows, plus overrides of hint visibility, item and choice randomization, timer visibility, and the tool list itself. Per tool: `PreventOverride` / `PadLock` flags. Resolution runs district/campus → assessment → item → student with locks available at each level, and there is a printable accommodations report and a TestHound integration flag. PIE's `PnpPolicySource` already expresses six precedence levels, so the shape is compatible; what PIE lacks is the authoring and lock semantics. This is the substance behind PIE-485 and PIE-486, and searching for "IEP" or "504" in the SchoolCity source finds nothing.

**Two secure-browser products, mutually exclusive per tenant.** Respondus LockDown Browser via an `ldb1:` custom URL protocol (`sc-online-testing/composables/exam/useLDBTest.ts`) and Microsoft Take a Test (`sc-suite-staff/WebContent/WEB-INF/Javascript/common/SCCF.js:3846-3883`, gated on `IsTakeATestSecureBrowserLicensed`). Neither appears in the master document. Adjacent to but distinct from PIE-483.

**Forced fullscreen.** `sc-online-testing/middleware/fullscreen.global.ts:21-24` auto-enters fullscreen on every exam route unless LockDown Browser is active. Best-effort — no re-entry detection or violation logging. This is PIE-492, which the report lists as uncovered, and it is a host-chrome concern rather than a toolkit one.

**A paper/online hybrid delivery mode.** The Online Bubble Sheet ("AKO", `sc-online-testing/pages/exam/ako.vue`) renders the assessment PDF in a pdf.js viewer while the student enters answers online. Staff-side print and bulk print choose a bubble-sheet vendor by delivery method — SchoolCity's own sheets or **GradeCam** — and there is a scanning module. PIE's print player is a different thing: it renders items to paper, with no answer-capture pairing. Relevant to the print-coverage limit noted under [Item-Level Tools](#item-level-tools).

**State-specific test modes.** `ShowSTAARTestMode` and `ShowFLORIDATestMode` restrict Desmos calculator behavior per program. PIE's calculator has an assessment/restricted mode but no program-keyed policy.

**Closed Captioning** is a real tool row in both legacy clients, checked against `<track>` elements, and absent from the Nuxt client — a SchoolCity internal parity gap. PIE has no captions capability either, though `captions` and `closedCaptions` exist in its PNP vocabulary.

Smaller student-facing surfaces with no PIE equivalent, all in `sc-online-testing`: an accented-character picker for Spanish and French input (`directives/characterPicker.ts`), an on-screen numeric keypad, a student-facing rubric viewer, teacher feedback notes surfaced to the student, a split-screen passage/question resizer, a progress thermometer, a review summary filtered by flagged items, offline and reconnect detection, a keepalive response save on unload, and LTI 1.0 launch with score post-back.

**What SchoolCity does not have**, grepped across all three repositories, because these bound PIE's gaps: no ASL or sign-language video anywhere; no audio recording (`MediaRecorder` absent, and a CKEditor `audioRecorder` toolbar button exists with no capture path behind it); no audio or video play-count limit or seek restriction; no masking tool; no scratchpad. PIE's shipped sign-language accommodation therefore exceeds SchoolCity rather than trailing it, and timed media is a gap against Learnosity's audio player only, not against SchoolCity.

### SchoolCity As A PIE Consumer

Both student clients already consume PIE, and the legacy one is coupled to player internals in a way that constrains pie-players. `sc-suite-student/StudentPortal.Web/Scripts/Exam/Exam.js:4903` and `:4919` read a response as `Array.from(playerapi?.children).find(c => c.tagName === 'PIE-PLAYER')?.session?.data[0]?.answer`. Any change to child-element structure, `session.data` shape, or the `answer` key breaks answer capture there, and the failure is swallowed into a `console.log` with `error.toString()` written into the stored response. The surface it depends on: `item-id`, `token` and `preview` attributes; `env` and `sessionId` properties; `score()` returning `{points, extraProps.correctResponse}`; and the `session-created`, `session-changed` and `load-complete` events. The Nuxt client goes through `@pie-api/pie-api-components` instead.

One consequence for the item-level table below: the legacy client hardcodes `partialscoring: false` into the PIE player env (`Exam.js:4866`, `:4877`). PIE's `multiple-choice` defaults partial scoring on, and this consumer turns it off unconditionally.

Highlighting itself is a core capability of the assessment toolkit, and PIE implements it with the modern CSS Custom Highlight API (`CSS.highlights` + `::highlight()`) rather than the legacy approach of wrapping selected text in `<span>` elements. ## Overlay Tools Versus Text-Interacting Tools

The master document makes a useful implementation distinction:

- Overlay/reference tools usually sit above or beside content and do not need to mutate item text. Ruler, protractor, periodic table, graph, line reader, and theme/color schemes mostly fall into this bucket.
- Text-interacting tools need selection, text range mapping, persistence, and sometimes content-language services. Highlighter, underline, dictionary, picture dictionary, translate selection, comments, custom speech, rollovers, and pop-ups fall into this bucket.

PIE is strongest in the overlay/reference bucket, and its current packaged tools already cover most of those capabilities. More important than the specific catalog of shipped tools, though, is that the assessment toolkit is a generic, application-independent framework for building them. Tools are registered against a shared contract (`ToolRegistration` / `ToolRegistry`, coordinated by `ToolkitCoordinator`) with PNP-driven tool policy, item/passage/section scoping, draggable/resizable tool shells, and visibility subscriptions, so a host or product can add its own tool using the exact same API as the built-ins. PIE ships a useful set of pre-fab tools, but standing up a new one is very doable — the section-demos app, for example, registers its own custom tools (such as a word counter) through the public registration API rather than forking the toolkit.

Just as important, cross-cutting concerns are solved once by the framework rather than re-implemented per tool. A single `ToolkitCoordinator` owns the shared services (tool policy, the `HighlightCoordinator`, `TTSService`, element tool state, and accessibility-catalog resolution); tools draw on common theming tokens (`--pie-*` variables and the `pie-theme` element) for automatic light/dark and high-contrast adaptation; highlighting runs through the one CSS Custom Highlight API layer; and capabilities such as `CSS.highlights` and `Intl.Segmenter` are feature-detected centrally with graceful fallbacks. A new tool therefore inherits consistent theming, accessibility, highlighting, policy, and capability-detection behavior without re-solving any of it.

The larger questions in the text-interacting and service-backed bucket are therefore less about whether PIE can build a given tool and more about decisions on selection range models, content ownership, persistence, language services, and whether a feature belongs in the toolkit, the assessment host, or item rendering.

## Text Editor, Equation Editor, And PIE Item Ownership

The master document calls out three ownership decisions:

- **Text editor**: choose a robust editor that meets product needs and works with the open-source PIE licensing model.
- **Equation editor**: SchoolCity has equation editor support, but ownership should likely shift toward PIE items and response editors if PIE is overhauling this area.
- **Custom speech / markup tools**: SchoolCity’s custom speech and markup affordances may need to be built into PIE item content or authoring flows rather than the generic assessment toolkit.

Those should not be treated as simple toolbar parity gaps. They affect item authoring, response capture, accessibility, content serialization, scoring, and licensing.

Because PIE elements already implement most of these as item-level model fields, the open product decision is less about building them and more about whether each should remain an item-level knob, move upward to assessment-level configuration, or be simplified or discontinued during migration. The genuine gaps here are narrower: author-configurable character limits and a distinct student-facing answer hint. Both were re-checked against `pie-elements-ng` for this refresh and both still hold, with the character limit now pinned to a hardcoded `50000`. Relative scoring is already handled by the PIE backend through `maxPoints` score scaling rather than a per-item knob.

Two limits on the element layer sit outside the master document's rows and bear on migration planning.

**Print coverage is partial.** 12 of the 30 elements export a `./print` subpath; 18 do not, including `graphing`, `charting`, `categorize`, `hotspot`, `drag-in-the-blank`, `number-line`, `matrix` and `placement-ordering`. The print player HEAD-checks for the module and, on a miss, renders a placeholder reading "Print module is not configured for this item type" (`packages/print-player/src/element-resolver.ts:88-94`) — so a paper form degrades element by element rather than failing, and the other items on the form print normally. A `fallback: "delivery"` for the print view is defined in the generic ESM loader (`packages/players-shared/src/loaders/esm-adapter.ts:41`) but the print player supplies its own view config without it, and the HEAD pre-check short-circuits before any import, so the fallback is unreachable from the print path. Given SchoolCity's paper and bubble-sheet delivery, this is a migration constraint rather than a cosmetic gap.

**The advertised delivery variants do not exist.** `../architecture/architecture.md:108-112` lists `delivery-mobile`, `delivery-a11y`, `delivery-simple` and `delivery-branded` as custom views enabled by package subpath exports, and `pie-elements-ng/docs/ARCHITECTURE.md:148-164` goes further, diagramming them as shipped peer folders. No element exports any of them; `BUILT_IN_VIEWS` defines exactly three — `delivery`, `author`, `print` (`packages/players-shared/src/loaders/esm-adapter.ts:38-42`). The mechanism is real and the variants are not, and there is live tooling in the demo apps that labels and tests for view names no package produces. A touch-optimized or accessibility-optimized delivery variant is available as a design, not as a shipped artifact.
